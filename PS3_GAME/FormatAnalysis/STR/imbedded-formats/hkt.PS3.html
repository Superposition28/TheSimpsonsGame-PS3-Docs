Game format research · PS3 EU reference baseline

Hkx-wrapped Havok 4 packfiles containing collision triangle meshes, MOPP acceleration data and some convex or box shapes. The inspected collision-directory set includes level collision; a collision file need not correspond to one visual model.

Identification
16-byte Hkx wrapper; Havok magic at file +0x10, packfile version 4 and Havok-4.1.0-r1 content version.
Byte order / text
Big-endian 32-bit integers/floats and 4-byte pointers for the inspected layout; names are null-terminated ASCII.
Documentation scope
2026-10-22: all 112 HKT paths in the supplied collision-directory list, 107 distinct SHA-256 values; every mapped Full/FullFlattened pair matched byte-for-byte.

Observed scope: the user's 401-path list selects files beneath directories literally named collision in ps3-eu-flattened. Its 112 HKT files range from 2,592 to 2,341,728 bytes. The current entire flattened dataset has 878 HKT paths, including 766 outside those directories; the following counts describe the selected list, not every HKT or every model collider. Wrapper, sections and fixups

All 112 selected HKT files and all 25 selected HKO files share this header. Unless a table says otherwise, offsets here are file-relative, fields are big-endian and ends are exclusive. H = 0x10 is the Havok packfile base: section absoluteDataStart values are absolute relative to H, not the beginning of the wrapped file.

File offset Bytes / type Meaning / observed value
0x00 16 bytes 48 6b 78 10 09 00 00 00 00 00 00 00 00 00 00 00; Hkx wrapper, remaining semantics unresolved.
0x10 UInt32 × 2 Havok magic 0x57e0e057, 0x10c0c010.
0x18, 0x1c UInt32 each User tag 0; packfile version 4.
0x20 4 bytes Layout rules 04 00 01 01: 4-byte pointers, big-endian, reuse-padding and empty-base optimization flags set.
0x24 UInt32 3 sections.
0x28–0x37 UInt32 × 4 Contents section 1, contents offset 0; contents-class-name section 0, string offset 0xd0 (EAPhysicsSystem).
0x38 16 bytes Havok-4.1.0-r1\0 and fill; content version, distinct from packfile version 4.
0x48 8 bytes ff fill.
0x50 3 × 48 bytes Section descriptors: __classnames__, __data__, __types__.

Each section descriptor has a 19-byte null-terminated tag and one fill byte, then seven UInt32 fields at descriptor +0x14: absoluteDataStart, localFixupsOffset, globalFixupsOffset, virtualFixupsOffset, exportsOffset, importsOffset, endOffset. The latter six are relative to that section's data start B = H + absoluteDataStart. Validate their monotonic order and B + endOffset ≤ file size. In this set __types__ is empty at EOF, while exports/imports have zero length.

Class-name records contain a UInt32 signature, byte 09, then a null-terminated ASCII name; ff fills the aligned tail. A virtual fixup refers to the string offset within the class-name section, not the preceding signature. The empty __types__ section means the files do not supply full member reflection layouts.

  • Local fixup: 8 bytes, (sourceOffset, targetOffset). Both offsets are relative to the current section's B.
  • Global fixup: 12 bytes, (sourceOffset, targetSectionIndex, targetOffset). Follow the named section; “global” does not mean another file. All inspected object pointers target the data section.
  • Virtual fixup: 12 bytes, (objectOffset, classNameSectionIndex, classNameStringOffset). These identify object classes; they are not triangle or pointer arrays.
  • Fixup regions end at the next declared boundary; their alignment tails are ff. Stop before padding, including partial final records. Stored pointer slots are zero in these files: follow fixups rather than reading zero as a valid file offset.

Collision mesh and shape layouts

The following are validated offsets within the inspected 32-bit PS3 class layout, relative to each object O. Array pointer slots resolve through the fixup tables. An hkArray-like triple is pointer, UInt32 count, UInt32 capacity/flags; observed capacity words commonly include 0xc0000000. Preserve those flags separately from the element count.

Class / O-relative field Observed interpretation
hkRigidBody +0x10, +0x1c Name-string pointer; shape pointer. A tree shape can then point to a mesh.
hkRigidBody +0xb0–+0xef 16 floats arranged as three padded basis vectors and a padded position vector; candidate authored transform. Runtime/world and bone-space interpretation still needs validation.
hkMoppBvTreeShape +0x10, +0x14 Child EAStorageMeshShape pointer and hkMoppCode pointer.
EAStorageMeshShape +0x14, +0x18 Vertex pointer and count. Each vertex is four Float32 values (16-byte stride); XYZ coordinates, W observed zero.
EAStorageMeshShape +0x20, +0x24 Triangle pointer and count. Each triangle is three UInt32 vertex indices (12-byte stride), not a four-word record or strip.
EAStorageMeshShape +0x38 Float32 value consistent with a convex margin (first example 0.01); exact query semantics unverified.
EAStorageMeshShape +0x40–+0xbf Eight padded XYZ vectors, consistent with expanded bounding-box corners. These are not the mesh vertex array.
EAStorageMeshShape +0xc0, +0xc4 Per-triangle material-pointer array and count. Each 4-byte slot resolves through a global fixup to an EAMaterial.
hkBoxShape +0x0c, +0x10 Float32 convex radius and padded XYZ half-extents. Preserve the margin separately; scaling dimensions by 1 + radius is an older viewer approximation.
hkConvexVerticesShape +0x0c, +0x10, +0x20 Convex radius, AABB half-extents vector and AABB center vector.
hkConvexVerticesShape +0x30, +0x34, +0x3c Four-lane vector-array pointer, group count and real vertex count. Each 48-byte group stores XXXX, YYYY, ZZZZ; trim padding lanes to the real count.
hkConvexVerticesShape +0x40, +0x44 Plane-array pointer and count; each plane is four Float32 values. Hull triangulation/query semantics were not reconstructed.

In all 8,054 inspected meshes, vertices begin at O + 0xd0 and triangles immediately follow the vertex array, matching the older viewer's fixed skip. Following fixups is still the safer format rule: it validates the array source and avoids generalizing that packing to other builds or shapes.

Extraction guidance and unknowns

For a first collision-geometry extractor, parse this wrapper and section layout, enumerate virtual fixups, follow body-to-shape and mesh-array fixups, then emit triangle meshes plus separate primitive/convex records. The explicit mesh arrays allow collision geometry to be recovered without interpreting or executing the MOPP bytecode. Preserve body names, raw transforms, material references and original units so model/scene associations can be resolved later. A whole level HKT can contain many bodies and need not match a preinstanced file by basename.

Matching paths and authored names suggest associations with preinstanced visual models and scene resources. This pass does not prove a complete join to render meshes, transform composition, axis/scale conversion, world placement, skeletal binding, motion modes, material response, contact filters or runtime loading. The other 766 HKT and 996 HKO resources outside literal collision directories need broader class/layout sampling before claiming complete suffix support.

Source-inspected tool evidence: the local reversing/TSGFileViewer/Scripts/Editor/Collision/CollisionLoader.cs and HavokReader/Classes/EAStorageMeshShape.cs already attempt partial mesh/box/sphere/convex visualization. They helped identify field candidates, now checked against the selected bytes. Their hardcoded skips, viewer Z flip, box origin and 1 + convexRadius scaling are implementation choices, not established original format semantics; the viewer does not reconstruct the complete physics system. No new engine importer was implemented by this investigation.

python -B tools/inspect_havok_collision.py --module-root ../.. --output research/2026-10-22-havok-collision.json

Run from the documentation root in a module checkout with both datasets present. Without --paths, the script selects HKT/HKO entries in literal collision directories from the normalizer map; --paths <text-file> restricts it to a supplied absolute flattened-path list. It validates bounds, fixups, class joins, geometry and canonical/alias identity without running the game or exporting model geometry. The retained report fingerprints the current map; the source registry's older map fingerprint remains a separately dated snapshot.

A:\RemakeEngine\EngineApps\Games\TheSimpsonsGame-PS3\GameFiles\STROUT\Map_3-00_SprHub\spr_hub\zone06_str\build\PS3\pal_en\assets\props\eps_mob_rules\mob_scaffolding\geo\export\mob_scaffolding_mr_unbuilt\collisionmodel.hkt.PS3

collisionmodel1.hkt.PS3 likly a Havok HKX packfile (big-endian PS3 build) that contains the physics/collision data for the prop spr_margesalonchair. The game's Havok runtime loads this alongside the RenderWare-rendered mesh to provide static collision, raycasts, and physics queries in the Game Hub interior.

  • Magic & header: starts with 48 6B 78 → "Hkx", followed by Havok-4.1.0-r1. That's Havok Content Tools 4.1 packfile metadata.

  • Packfile sections: literal section labels:

    • __classnames__, __data__, __types__ -- classic Havok tagfile/packfile layout.

  • Havok class table: many baked type names:

    • hkClass, hkClassMember, hkClassEnum, ...
    • Physics/shape types: hkRigidBody, hkBvTreeShape, hkMoppBvTreeShape, hkSimpleMeshShape, hkStorageMeshShape, hkShapeContainer, hkMotion, etc.

  • Asset name string: spr_margesalonchair|MetaModel|Asset|CollisionModel1|...|v3 -- clearly labels this file as the collision model for that prop.

  • Geometry + tree: you can see BE floats and index lists (vertex data / triangle indices) and a MOPP BVTree block -- Havok's static-mesh acceleration structure for collisions.

What it's for

  • Acts as the physics representation of the chair prop:

    • A static rigid body (fixed motion) built from a mesh shape wrapped in a BVTree/MOPP for fast queries.
    • Used for character/controller collision, line-of-sight/raycasts, projectile hits, and placement/blocking.

  • Loaded by the game's Havok integration while the RenderWare side draws the visual mesh. The two are associated via the shared asset naming/path.

related extensions:

  • .hkt.PS3 all regular collision files have this extension
  • .hko.PS3 all animated collision files have this extension, and all character collision spheres use this extension
  • .acs.PS3 always contained within collision folders (or subfolders of it) often alongside .hko.PS3 files
