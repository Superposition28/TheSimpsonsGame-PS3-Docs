Game format research · PS3 EU reference baseline

Compact character/weapon collision records with binding identifiers, transform-like floats and primitive parameters. These records contain no triangle mesh and are distinct from the Havok HKT/HKO packfiles.

Identification
Observed header 01 count 00 00, followed by length-prefixed records. No universal magic established.
Byte order / text
Big-endian record lengths, identifiers and IEEE-754 floats; byte-sized header/tag interpretations are sample-derived.

Inspected corpus and provenance

The 2026-10-22 user-supplied list contains 401 files beneath directories named collision: 264 ACS, 112 HKT and 25 HKO. It exactly matches that directory-name scope in the current ps3-eu-flattened tree. Every listed file has a unique mapping to ps3-eu-extracted and an identical canonical byte sequence. This is a bounded inventory, not every collision resource in the game: the canonical Full collision directories retain three additional weapon ACS files and two costume HKO files absent from this alternate view. Their paths are listed in the provenance ledger.

Observed record layout

All 264 inspected headers begin with 01, have a record count at byte +1, and end with two zero bytes. Treat +0 as a candidate version byte and +2..3 as uninterpreted zeros. Records start at file 0x04; each first word is its complete size, including that word. Advance by the declared size rather than a fixed stride. All declared records end exactly at EOF in this corpus.

Offsets relative to the start of an ACS record
Offset Bytes / encoding Observed interpretation and limits
+0x00 4 / BE u32 Total record size: 80 (0x50) or 84 (0x54).
+0x04 4 / identifier Stable record identifier; name/hash meaning unresolved.
+0x08 4 / BE u32 Binding identifier. Bunny values match BBN alias hashes and lowercase SDBM of the corresponding alias strings.
+0x0C 4 / opaque bytes Five observed patterns: 00064300, 00000100, 00020100, 00004000, 00060100. Flag subdivision and meanings unknown.
+0x10 4 / opaque bytes 00 73 00 00 in every record, including all three kinds. The 73 byte is not an observed sphere/capsule discriminator.
+0x14 4 / identifier Additional identifier or zero. No verified material, bone or shape-name lookup.
+0x18 48 / 12 BE f32 Three basis-like triples followed by a translation-like triple. Identity is (1,0,0), (0,1,0), (0,0,1), (0,0,0). Row/column convention, handedness and world units require validation.
+0x48 1 + 3 Candidate kind byte 01, 02 or 03, followed by three zeros. Preserve all four raw bytes; enum storage is not established by runtime code.
+0x4C 4 or 8 / BE f32 Kind 1: one scalar, size 80. Kinds 2 and 3: two scalars, size 84. Scalar units and exact geometry remain inferred.

Counting duplicate files, the corpus contains 1,505 records: 1,341 kind 1, 121 kind 2 and 43 kind 3. Kind 1's positive scalar is consistent with a sphere radius. Kind 2 occurs on elongated weapons, commonly with (0.1, 0.7); capsule-like radius/length is a hypothesis. Kind 3 occurs in Homer, Lisa, Lard Lad and Selmatty resources with different scalar pairs; a cylinder/capsule or gameplay-volume interpretation is unresolved. No observed 'c' tag is needed to walk these variants.

The transform-like block has six distinct values in this corpus. Alien knee records include opposite X offsets and a shared -0.5 Z offset; weapon saw/cane records have non-identity basis triples. These examples support a local transform interpretation, but do not determine a target engine's coordinate conversion.

Collision extraction implications

For terrain and prop triangle collision, start with HKT's Havok shape graph, including EAStorageMeshShape vertex/index arrays. ACS is a separate primitive/binding path. The shared HKO sample provides boxes and spheres; its filename does not identify the geometry of every contained shape.

An ACS viewer can already show identifiers, transforms and scalar parameters. For the bunny, the BBN-to-HAnim identifier lookup is established, but correctly attaching candidate spheres still requires resolving and applying bone transforms. A direct file pointer or original runtime selection of these visual LODs from ACS has not been recovered. Bone poses, scale, shape-kind semantics and gameplay flags must be resolved before treating a preview as original collision behavior.

The expanded name “Articulated Collision Shapes” remains a historical hypothesis. Record boundaries and the bunny BBN join are now byte-validated; exact shape geometry, flag behavior, model coordinate transforms and a game-module collision importer remain unresolved. No original game runtime execution was observed.

Detailed field tables and retained samples are research evidence. Implementation-derived observations must remain attributed to their tools; tentative, observed and contextual relationships do not establish complete original runtime behavior. Offsets in the added tables are zero-based; range ends are exclusive unless stated otherwise.

Format: ACS — per-character Articulated Collision Shapes (PS3)

marge.acs.PS3 is a small, binary list of simple hit-shape primitives (mostly spheres/capsules) attached to a character’s bones. The game uses this to do lightweight gameplay collision (melee hits, pickups, proximity checks, cursor targeting, etc.) without touching the full Havok meshes.

Why this is ACS / hit-spheres

  • The path: assets\shared\collision\marge.acs.PS3 → per-character collision set.

  • You see lots of IEEE-754 floats like:

    • 3F 80 00 00 = 1.0 (identity scale/weights),
    • 3E 99 99 9A ≈ 0.30, 3E 80 00 00 = 0.25, 3F C0 00 00 = 1.5, 3D CC CC CD = 0.1 — typical radii for gameplay spheres.

  • Repeating fixed-size records with very similar layouts (centers/flags/identity), suggesting “one primitive per bone”.

What the game uses it for

  • Hit detection / hurtboxes for punches, kicks, and small overlaps.
  • Targeting helpers for abilities and cursor hover.
  • Cheap per-bone checks while Havok handles full body collision separately (your .hkt file).

Rough layout you’re seeing (per entry)

Not exact names, but the pattern maps like this for each shape:

  • A small header/IDs (includes a bone or binding hash; EA often stores CRCs of bone names).
  • A primitive type code (you’ll spot 0x73 00 00 → 's' = sphere; some titles also use 'c' for capsule).
  • Center/orientation-ish block (many 1.0 values → identity) and/or flags.
  • A radius (those 0.25 / 0.30 / 0.10 / 1.50 values).
  • Repeats for each bone hotspot (head, hands, forearms, torso, legs, etc.).

In short: .acs.PS3 = fast hit-shape set—a handful of bone-attached spheres (and possibly capsules) used by the EA/RenderWare runtime for quick overlap tests and gameplay interactions on PS3.
