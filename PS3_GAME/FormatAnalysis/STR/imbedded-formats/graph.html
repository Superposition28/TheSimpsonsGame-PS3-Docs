Operation and editor-import support

The Godot project enables addons/tsg_graph_importer/plugin.cfg. Its editor plugin registers import_graph.gd as tsg.graph.importer, visible as TSG NavGraph, for the graph extension. The importer saves TSGNavGraph as a binary .res resource at the editor-supplied import-cache path.

The resource exposes guid: String, nodes: Array[Dictionary] and edges: Array[Dictionary]. NavGraphVisualizer can consume it to draw nodes as crosses and edges as straight lines, with visibility/color controls. Importing does not construct an AStar3D, a navigation mesh or an original-game AI controller.

No GRAPH converter is registered in operations.toml; that does not mean import support is absent. Operation 1 extracts the source payload and operation 6 can normalize its path. The Godot editor import is a separate code path. See the operation pipeline for the registered operations.

Evidence and limitations

Partial import is implemented in the supplied Godot source. Edge-table boundaries are selected heuristically, unknown fields are discarded, and parsing can stop early on invalid data. Saving a resource is not proof that every node/edge or original navigation behavior was recovered. These changes were checked against source code; the editor import was not rerun in this documentation pass.

The tables below describe what the current importer reads and retains, rather than assigning unverified runtime meanings. They supersede the older ConnStartIndex/NeighborCount node interpretation and the fixed ConnectionCount/Blocked edge interpretation previously shown here.

The implementation treats these resources as navigation-graph data. The fields below document its current parsing model; unknown semantics remain unknown.

File header and array locations

The importer requires a file of at least 0x80 bytes and explicitly sets big-endian reads. Header offsets are absolute file offsets; range ends below are exclusive.

Header locations used by the Godot importer
OffsetRead typeUse in the implementation
0x00–0x0B12 bytesNot decoded; the importer does not check a format magic.
0x0Cuint32 BEHigh 16 bits become node_count. The low 16 bits at 0x0E are not used to determine edge count.
0x10byte[16]GUID bytes, formatted as an uppercase braced 8-4-4-4-12 hexadecimal string.
0x20uint32 BEnode_offset; zero/out-of-file values disable the node-read loop.
0x24uint32 BEFirst candidate node-array end, accepted only when in range and 32-byte aligned relative to node_offset.
0x40, 0x44, 0x48uint32 BE eachCandidate later block offsets used to limit edge scanning.
0x60 / 0x64uint32 BE eachBlock-offset candidate at 0x60 is considered for edge scanning only when the count-like value at 0x64 is positive.
0x68uint32 BEAlternative candidate node-array end; also considered as a later block boundary.
0x70uint32 BEAdditional candidate later block boundary.

Node structure

32-byte node record; multi-byte values are big-endian
Relative offsetTypeResource field / behavior
0x00, 0x04, 0x08float32 eachX, Y, Z retained as pos: Vector3, without axis remapping or scaling.
0x0Cfloat32radius
0x10uint16node_id
0x12int16area; converted from the unsigned read to signed 16-bit.
0x14uint32flags; retained as a raw integer.
0x18–0x1Fbyte[8]Skipped; not retained in the resource.

The node loop attempts the header's node_count, stopping if the next 32-byte record exceeds EOF. It does not use the chosen node_end as a hard boundary for this loop, so a malformed header may still produce incomplete or misclassified data. The node_id value is stored separately from the array indices used by the edges.

Edge structure and detection

16-byte edge candidate; multi-byte values are big-endian
Relative offsetTypeResource field / behavior
0x00float32cost
0x04uint16a: node-array index
0x06uint16b: node-array index
0x08int16tag_c
0x0Auint16tag_d
0x0Cuint32Read into a variable named zero, but neither validated nor retained.

The initial node_end is node_offset + node_count × 0x20. A plausible aligned value at 0x24 takes precedence; 0x68 is a fallback. The selected end is clamped to the file range. Edge candidates are scanned from that position up to the earliest accepted later block offset, or EOF if none is found.

Scanning stops at the first candidate whose a/b index is outside the declared node count, whose indices are equal, or whose cost is NaN or has absolute value above 1,000,000. The importer does not prove edge directionality, tag meanings, a universal edge count or the meaning of the discarded final word. It does not interpret that word as a validated Blocked boolean.

Godot resource use and source references

With the supplied editor plugin enabled, a .graph file inside the Godot project is handled by TSG NavGraph and saved as a resource with the exported GUID/nodes/edges fields. Assigning that resource to a NavGraphVisualizer's nav_data property provides the implemented node/edge display. This visualizer uses the stored positions directly; it does not establish a verified transform to BSP or other level data.

  • plugin.gd registers/unregisters the editor import plugin; plugin.cfg supplies its metadata.
  • import_graph.gd implements the big-endian parser, candidate-boundary checks and resource save.
  • tsg_nav_graph.gd defines the serializable TSGNavGraph resource.
  • Scripts/nav_graph_visualizer.gd consumes that resource to draw crosses and lines.
