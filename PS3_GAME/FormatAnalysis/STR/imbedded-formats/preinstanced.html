Preinstanced Asset Format (EARS_MESH) - Complete Implementation Guide

Version: 2.1

Last Updated: 2026-10-02

Author(s): samarixum (based on reverse-engineering research)

Overview

  • Format Name: Simpsons Game Preinstanced Asset / EARS_MESH
  • Common File Extension(s): .dff.preinstanced, .rws.preinstanced (embedded in STR sections)
  • Purpose/Domain: Defines 3D model geometry, multiple UV maps, and texture name associations for assets in The Simpsons Game (PS3).
  • Originating Application/System: A heavily modified version of RenderWare customized by EA for The Simpsons Game.
  • Format Type: Binary, sequential chunk-based (no global header).
  • General Structure: The importer scans for RenderWare string chunks, TLFD markers, EA mesh anchors, and an EOF marker. Current Blender parsing associates names occurring before mesh anchors; it detects but does not currently use TLFD markers to build material groups.
  • Endianness: Mixed-Endian. Almost all data is Big-Endian, except for FaceDataOff and MeshDataSize in mesh chunk headers (Little-Endian).

Parsing Algorithm Overview

  1. Scan file sequentially from byte 0 to EOF
  2. Scan for validated length-prefixed RenderWare string chunks, TLFD markers, mesh anchors, and the EOF marker.
  3. Collect texture-name events and associate names preceding each mesh marker using the current flat-list behavior.
  4. For each mesh anchor, parse the counts and submesh pointer records, then follow each pointer to its submesh header and vertex-info block.
  5. Validate every buffer range against the enclosing file and the declared vertex stride.
  6. For each detected event:
    • Texture string → Add its name to the list used for the next mesh.
    • TLFD marker → Record for analysis; it is not yet used as a material-group boundary.
    • Mesh anchor → Parse submeshes and associate names found since the preceding mesh.
    • EOF Marker → Stop parsing
  7. Return meshes with provisional texture bindings.

Current Working Assumptions

  • Submesh table 8-byte prefix: The repeated 8-byte value before each submesh offset is not a texture index. Latest dumps show it is stable across many files and looks more like a structural marker than a selector.
  • Submesh header interpretation: The 12-byte block at MeshChunkStart + SubmeshRelOffset is not entirely unknown. Bytes 0-3 look like vertex/primitive flags, bytes 4-7 appear to be a bounding volume or frustum radius float, and bytes 8-11 behave like a zero-based material index.
  • Texture/material grouping: The importer currently stores a flat, ordered list of texture names per mesh and selects a name using material_id * 2, with a palette special case. Real files show variable numbers of names and TLFD markers; this pair rule is not established as a format invariant.
  • Mapping caveat: Texture assignment is incomplete. Treat current material bindings as provisional until per-material groups have been checked against known-good assets.
  • Vertex attributes: Positions and UV fields are read at fixed offsets when they fit the declared stride. Other bytes may contain normals, prelit colors, or skinning data, but their meanings have not been confirmed for all DFF/RWS samples.
  • DFF/RWS distinction: The Blender addon currently handles both extensions through the same preinstanced importer. The separate C++ readers are prototypes; their differences are not sufficient to define the complete on-disk distinction.

Observed Chunk Signatures

The C++ Chunk helper reads type, size, and version as little-endian UInt32 values and recognizes EA type 0x0000EA33. The Blender addon uses byte-pattern anchors rather than a recursive RenderWare chunk reader. These interpretations describe observed reader behavior and byte patterns, not a complete proof of every enclosing hierarchy.

01 00 00 00 04 00 00 00 2D 00 02 1C followed by four bytes Observed rwID_STRUCT with a four-byte payload and version stamp, before a string chunk. Validated by the structured name parser across TEST files. The enclosing material/texture parent chunk is not decoded here.

Texture Name String Chunks

The current parser recognizes a RenderWare rwID_STRUCT chunk with a four-byte payload, followed by an rwID_STRING chunk. The version stamp observed in both chunk headers is 2D 00 02 1C. Four filter/address bytes occur in the struct payload; the string chunk then supplies its own byte length and payload. The parser validates chunk types, sizes, version stamps, bounds, and printable ASCII rather than requiring one exact filter value.


    rwID_STRUCT: 01 00 00 00 | 04 00 00 00 | 2D 00 02 1C | [4 filter/address bytes]
    rwID_STRING: 02 00 00 00 | [length UInt32 LE] | 2D 00 02 1C | [length bytes: ASCII, NUL, optional 0xBF fill]

Across the current TEST tree (5,533 preinstanced files), the structured scanner found 34,945 valid names, compared with 31,920 matches from the former three exact signatures. Observed filter/address bytes were 02 11 01 00 (34,784 occurrences) and 01 11 01 00 (161 occurrences). Validated string payload lengths were 0x04, 0x08, 0x0C, 0x10, 0x14, 0x18, 0x1C, and 0x20. A four-byte payload can be the valid three-character name apu followed by its NUL terminator. Other lengths up to the parser's defensive 0x80-byte cap remain accepted only when chunk structure and bounds are valid.

Texture List Delimiter (TLFD)

54 4C 46 44 (ASCII "TLFD")

Observed behavior: The marker is detected between string and mesh events. The current importer logs TLFD events but does not yet use them to partition material groups. Grouping by TLFD is under validation against saved Blender references.

Mesh Chunk Signature

33 EA 00 00 followed by 4 bytes (wildcard), then 2D 00 02 1C

Pattern: 33 EA 00 00 ?? ?? ?? ?? 2D 00 02 1C

Function: Marks the start of a mesh chunk header.

EOF Marker

16 EA 00 00 05 00 00 00 2D 00 02 1C 01 00 00 00 00

Function: Signals end of valid file data. Parsing should stop here.

Texture Name Extraction

Location: Inside the payload of a validated rwID_STRING chunk following the texture-name struct chunk. The string chunk carries a little-endian byte length; payloads may contain a null terminator and 0xBF padding.

Current parser behavior: Require the preceding rwID_STRUCT type, its four-byte payload size, and the observed version stamp in both headers. Read only the bounded string payload, stop at NUL, trim trailing 0xBF padding, and accept the supported filename characters. Texture-name events are associated with following meshes; TLFD is recorded but not yet used for grouping.

DFF and RWS Notes

The Blender addon uses the same preinstanced scanner for both extensions. The current C++ source has separate DFFOpen and RwsOpen classes with largely parallel chunk/geometry code. Although DFFOpen declares a HasSkin member, its current chunk walk does not process a SkinPLG; do not treat this as working skin support. Neither implementation alone establishes that all DFFs are single-clump/skinned or all RWS files are multi-clump/two-UV. Confirm extension-specific claims with representative extracted samples before treating them as format rules.

Mesh Chunk Header Structure

Location: Starts at the byte after the mesh chunk signature (33 EA 00 00 ?? ?? ?? ?? 2D 00 02 1C).

The current readers treat the word at mesh-anchor offset +0x04 as a little-endian chunk-size candidate. The version stamp and count/pointer fields described below are read separately; exact RenderWare chunk semantics for the custom mesh record still need sample validation.

Header Layout

Offset (Abs) Offset (Rel) Size Type Endian Field Name
0x00 - 4 UInt32 LE Signature (33 EA 00 00)
0x04 - 4 UInt32 LE candidate MeshChunkSize
0x08 - 4 UInt32 LE Signature Verify (2D 00 02 1C)
0x0C 0x00 4 UInt32 BE Unknown Header Word
0x10 0x04 4 UInt32 LE FaceDataOff
0x14 0x08 4 UInt32 LE MeshDataSize
0x18 0x0C - - - MeshChunkStart (Header Base)

FaceDataOff is used by the importer as a shared base for both vertex and face buffers: MeshChunkStart + FaceDataOff + relative_buffer_offset. MeshDataSize is read but is not used by the importer to bound those buffers. Its exact extent and the proposed identity with the enclosing size word remain unverified.

Navigation Table and Sub-Meshes

MeshChunkStart is absolute offset 0x18, immediately after the 12-byte mesh anchor and the two little-endian fields. The current addon, viewer, and C++ readers skip 0x14 bytes from this base, then read TableCount at relative +0x14 (mesh-anchor offset +0x2C) and SubmeshCount at relative +0x18 (mesh-anchor offset +0x30), both big-endian.

Offset (Rel to Base) Size Type Endian Field Name
0x14 4 UInt32 BE TableCount
0x18 4 UInt32 BE SubmeshCount

Sub-Mesh Table Entries

Located at MeshChunkStart + 0x1C + TableCount * 8. Each submesh table entry is 12 bytes and contains an 8-byte prefix followed by a big-endian relative pointer to a separate submesh header.

Offset (Sub-Mesh) Size Type Field Name Description
0x00 8 Byte[8] UnknownPrefix Meaning not decoded.
0x08 4 UInt32 SubmeshRelOffset Big-endian relative offset from MeshChunkStart to a separate submesh header.

Pointed-To Submesh Header

Located at MeshChunkStart + SubmeshRelOffset. The current readers consume this 12-byte header, then read the vertex-info relative pointer at its +0x0C field.

Offset (relative) Size Type Name Description
0x00 4 UInt32 BE Flags Interpretation not confirmed.
0x04 4 Float32 BE BoundsValue Candidate bounds/radius value; meaning not confirmed.
0x08 4 UInt32 BE MaterialId Ordinal read by the importer. Its mapping to material/texture groups is unresolved.
0x0C 4 UInt32 BE VertexInfoRelOffset Relative offset from MeshChunkStart to the vertex-info block.

Vertex Information Structure

The big-endian VertexInfoRelOffset is stored at SubmeshHeader + 0x0C and is relative to MeshChunkStart. Following that pointer:

Offset (VertInfo) Type Endian Field Name Description
0x00 UInt32 BE VertTotalSize Total size of vertex buffer.
0x04 UInt32 BE VertStride Bytes per vertex (stride).
0x10 UInt32 BE VertStartRel Offset to vertex data (relative to FaceDataOff).
0x28 UInt32 BE FaceByteLen Total size of face index buffer (bytes).
0x30 UInt32 BE FaceStartRel Offset to face data (relative to FaceDataOff).

Mesh Data Extraction

Vertex Buffer

Location: MeshChunkStart + FaceDataOff + VertexStart.

Vertex Count: VertChunkTotalSize / VertChunkSize

Observed vertex fields (per vertex, Big-Endian floats): UV0 is available when VertChunkSize >= 0x1C. UV1 is available when VertChunkSize >= 0x24; the importer now defaults a missing channel rather than reading into the next vertex. The flag byte in the geometry struct includes a prelit bit, but its relationship to these bytes and the proposed edge-culling use have not been validated on sample assets.

Offset Size Type Field Description
0x00 12 float[3] Position (X, Y, Z) 3D vertex coordinates.
0x0C 4 bytes[4] Candidate Packed Normal Possible packed normal when geometry-normal flags are set; encoding and presence are not confirmed.
0x10 4 bytes[4] Candidate Prelit Color May be a prelit RGBA color when the corresponding geometry flag is set. Color order and edge-culling interpretation are unverified; the addon does not currently import this field.
0x14 4 float UV0 U (Primary Texture) U coordinate for main texture map.
0x18 4 float UV0 V (Primary Texture) V coordinate. Must flip: (1.0 - V) for proper rendering.
0x1C 4 float UV1 U (Secondary/CM Texture) U coordinate for secondary (color/environment map).
0x20 4 float UV1 V (Secondary/CM Texture) V coordinate. Must flip: (1.0 - V).
0x24+ VertChunkSize - 36 (when stride exceeds 0x24) bytes[N] Additional Attributes Additional attributes may include more UV channels, skinning data, or other fields; layout is not established. DFF skin/plugin handling must be checked per sample.

Face/Index Buffer

Location: MeshChunkStart + FaceDataOff + FaceStart.

Index Count: FaceDataByteLength / 2

Index Structure (per index):

  • 2 bytes UInt16 (Big-Endian): Vertex index
  • Special Value: 0xFFFF (65535) is a "strip cut" delimiter. This marks the end of one triangle strip and the start of another. It should not be rendered as an index.

Triangle Strip Conversion Algorithm:

Split the index stream at 0xFFFF before triangulating. Keep the final strip even when the stream has no trailing sentinel. The current addon skips repeated-index degenerate triangles and toggles winding parity for each candidate triangle.

The separate C++ readers do not append the final unterminated strip in their current loops and do not filter repeated-index degenerate triangles. Those prototype limitations do not describe the Blender addon's behavior.


strips = []
current_strip = []
for index in indices:
    if index == 0xFFFF:
        if current_strip:
            strips.append(current_strip)
        current_strip = []
    else:
        current_strip.append(index)
if current_strip:
    strips.append(current_strip)

triangles = []
for strip in strips:
    flipped = false
    for i from 0 to len(strip) - 3:
        v1, v2, v3 = strip[i], strip[i + 1], strip[i + 2]
        if v1 == v2 or v1 == v3 or v2 == v3:
            flipped = not flipped
            continue
        if flipped:
            triangles.append((v3, v2, v1))
        else:
            triangles.append((v2, v3, v1))
        flipped = not flipped

Complete Parsing Example (Pseudocode)


function parse_preinstanced(file_data):
    meshes = []
    active_texture_names = []
    has_seen_texture_since_mesh = false

    pos = 0
    while pos < len(file_data):
        if is_rw_string_chunk_at(file_data, pos):
            name = read_bounded_ascii_rw_string(file_data, pos)
            if name:
                if not has_seen_texture_since_mesh:
                    active_texture_names = []
                    has_seen_texture_since_mesh = true
                active_texture_names.append(name)
            pos = end_of_rw_string_chunk(file_data, pos)
        elif file_data[pos:pos+4] == "TLFD":
            record_tlfd_event(pos)
            pos += 4
        elif matches_mesh_anchor(file_data, pos):
            mesh_start = pos
            has_seen_texture_since_mesh = false
            mesh_textures = copy(active_texture_names)
            mesh_chunk_start = mesh_start + 0x18
            face_data_off = read_u32_le(mesh_start + 0x10)
            mesh_data_size = read_u32_le(mesh_start + 0x14)  // Extent not yet verified

            table_count = read_u32_be(mesh_chunk_start + 0x14)
            submesh_count = read_u32_be(mesh_chunk_start + 0x18)
            table_start = mesh_chunk_start + 0x1C
            submesh_table_start = table_start + table_count * 8

            for submesh_index in range(submesh_count):
                entry = submesh_table_start + submesh_index * 12
                submesh_rel = read_u32_be(entry + 8)
                submesh_header = mesh_chunk_start + submesh_rel
                material_id = read_u32_be(submesh_header + 8)
                vertex_info_rel = read_u32_be(submesh_header + 0x0C)
                vertex_info = mesh_chunk_start + vertex_info_rel

                vertex_total_size = read_u32_be(vertex_info + 0x00)
                vertex_stride = read_u32_be(vertex_info + 0x04)
                vertex_start_rel = read_u32_be(vertex_info + 0x10)
                face_byte_length = read_u32_be(vertex_info + 0x28)
                face_start_rel = read_u32_be(vertex_info + 0x30)

                vertex_buffer = mesh_chunk_start + face_data_off + vertex_start_rel
                face_buffer = mesh_chunk_start + face_data_off + face_start_rel
                require_in_bounds(vertex_buffer, vertex_total_size)
                require_in_bounds(face_buffer, face_byte_length)

                for vertex in range(vertex_total_size // vertex_stride):
                    stride_start = vertex_buffer + vertex * vertex_stride
                    position = read_float3_be(stride_start + 0x00)
                    uv0 = read_float2_be(stride_start + 0x14) if vertex_stride >= 0x1C else DEFAULT_UV
                    uv1 = read_float2_be(stride_start + 0x1C) if vertex_stride >= 0x24 else DEFAULT_UV

                indices = read_u16_be_array(face_buffer, face_byte_length // 2)
                strips = split_on_sentinel(indices, sentinel=0xFFFF)
                triangles = build_triangle_list(strips)  // Keep cuts; flush final strip

                meshes.append({
                    name: unique_mesh_name(mesh_start, submesh_index),
                    material_id: material_id,
                    textures: mesh_textures,
                    triangles: triangles
                })

            pos = mesh_start + 1  // Continue the anchor scan; MeshDataSize is not used as a bound
        elif matches_eof(file_data, pos):
            break
        else:
            pos += 1

    return meshes

Validation Rules

  • Vertex Count: Must be > 0. If 0, mesh is invalid.
  • Triangle Count: Validate the result after splitting on 0xFFFF, discarding strips shorter than three indices, and filtering repeated-index degenerates.
  • Index Bounds: All non-delimiter indices must be < vertex_count.
  • VertChunkSize: Must be positive and fit each attribute read within the current vertex record; UV0 and UV1 are optional based on stride.
  • Endianness Check: If vert_chunk_size appears impossibly large (> 1000), may have endianness error. Verify byte order.
  • Texture Association: Texture names, TLFD events, submesh material IDs, and material slots need cross-checking against a known-good imported asset; do not infer a two-name-per-material rule from counts alone.

Known Limitations & Unknowns

  • mDataTable: Latest dumps do not support the old texture/material ID hypothesis. It looks more like an offset/flag table, but the exact semantics are still unclear.
  • Texture assignment: The current material_id * 2 selection with a palette special case is a heuristic. Real files contain variable name counts and material IDs; TLFD grouping and material ordinal semantics remain under validation.
  • FaceDataOff / MeshDataSize: Readers use FaceDataOff as a shared base for vertex and face buffers. The importer reads MeshDataSize but does not use it as a validated bound; its full extent and relation to the mesh anchor size are unresolved.
  • Full Vertex Stride: Position and UV offsets are read when they fit the declared stride. Candidate packed normals, prelit colors, additional UVs, and bone data have not been fully identified. The edge-culling interpretation of vertex colors is unverified.
  • Mipmap Handling: Not addressed in this format. Assume single resolution.
  • Bone/Skinning Data: Skinning data has not been decoded by the Blender addon. The current C++ DFF source declares a skin flag but does not process a SkinPLG in its chunk walk.
  • Validation anchors: check12.py contains long-form header patterns for the SOF main, second, and third headers. These are useful for sanity-checking file families, but they should be treated as validation anchors rather than canonical field definitions.
  • Shared section markers: The repeated family 13/15/16/33 EA 00 00 ... 2D 00 02 1C is useful when tracing section boundaries. The viewer highlights these as shared/unknown section headers until the exact semantics are confirmed.
