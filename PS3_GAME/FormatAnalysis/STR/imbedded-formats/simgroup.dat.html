SimGroup and other STR-generated .dat payloads

Source scope: PS3 EU remains the reference baseline. The 2026-10-19 supplementary investigation examined original PS3 US STR bytes and individual QuickBMS extractions, plus an existing EU extraction snapshot locally labeled 1PS3-EU-Full-audio_reorg-isRenamed/. That historical local label and its generated filenames are retained here; they are not original archive-member names. See roots and provenance and the investigation evidence.

Game format research · PS3 EU baseline with labeled PS3 US observations

SimGroup records define entity groups, behaviors and attributes. Numbered .dat outputs also include a separate UIE resource family.

Identification
Use the containing STR record and payload bytes. 0x2207 bodies have SimG at +0x08; legacy dumps place it at +0x04. The generated .dat suffix alone identifies neither structure.
Byte order / text
SimGroup header words and entity references are big-endian. Inspected UIE entries use little-endian keys and GUID words. Attribute-mask byte order remains an attributed parser observation.
Documentation scope
Updated 2026-10-19 from source-byte audits, extraction comparisons and inspected viewer code. Record identification and extraction are better established than runtime semantics.

Tools and integrations

The inspected reversing/TSGFileViewer/Scripts/EAStreamFile.cs recognizes 0x2207 and passes its complete body to SimGroup.cs. It skips interpretation of headerless 0x1607 payloads and leaves compact 0x2307 assets unimplemented. Its registered resource handlers contain no UIE handler.

Optional Remake Engine implementation notes describe the extractor's generated naming and output contract. Those conventions are separate from original resource names and runtime behavior.

Evidence and limitations

The supplementary audit of all 490 inspected US source STR files found 25,927 0x1607 assets and 452 0x2207 records. All 452 had SimG at body +0x08, version 1, two leading zero words and ppEntPackets = 0x30. Eighteen 0x1607 assets had an empty metadata path and resource type UIE. These counts describe this source set, not every release.

The existing EU snapshot contained 434 numbered DAT files: 416 beginning with 00 00 00 00 53 69 6D 47 00 00 00 01 and 18 distinct non-SimGroup payloads. Legacy dumps could concatenate later records, so 416 is a count of files beginning with a SimGroup, not a count of all simulation groups. Original EU archive membership is not inferred solely from renamed output folders.

The tables combine US source-byte observations with the field interpretation implemented by SimGroup.cs. Entity IDs and resource references require the correct level context. Unknown words, flag meanings, shared-data/dictionary semantics, attribute defaults and original runtime lookup rules remain unresolved. Offsets are zero-based; lengths are bytes.

Source paths, hashes, extraction comparisons and EU sample headers are retained in unnamed-payload-evidence.json. The reference remains readable without the local game files or viewer.

Why numbered DAT files were generated

The legacy QuickBMS script passed an empty output name to log through two different routes. QuickBMS supplied a numbered .dat filename; the digits were extraction-generated and could change with extraction order or existing output files. Neither route establishes an unknown or corrupt payload.

Source record Why the output name was empty Observed payload
0x2207 The script applied the 0x1607 metadata-header interpretation to another record type. The first body word was zero, so it selected the “no header” branch. This SimGroup record has no embedded asset pathname to extract. SimGroup body with its first four bytes removed, followed by any remaining records in the section.
0x1607, type UIE The metadata subheader existed, but its file-path string was empty. In the inspected US loc/loc.str sample the object name was World, the type was UIE, and HeaderSize was 72. A separate 60-byte payload of three 20-byte UIE entries. Its payload bytes were extracted correctly; the filename was synthetic.

Legacy boundary error: the zero-header branch used the entire remaining decompressed section as its length. It consumed later record envelopes and stopped extracting their contents separately. Manual extraction of US PS3_GAME/USRDIR/loc/loc/Story_Mode/Story_Mode_Design.str produced 225 outputs with the legacy script and 229 after record-boundary handling was corrected: four distinct SimGroup bodies and a later 0x1607 StreamSetConfig asset were recovered separately. The four SimGroup record starts in section 10 were 0x3820C, 0x3EA08, 0x40EE0 and 0x4DBC4. These are decompressed-section offsets. The later StreamSetConfig had a duplicate metadata path; preserving both payloads also required collision handling.

The corrected extractor distinguishes these record families, retains each complete SimGroup body and uses its outer little-endian body length to continue at the next record. Synthetic names identify section/record position; they do not recover an original filename. The exact output naming contract is documented in the integration notes.

SimGroup header and offset bases

A 0x2207 record has the common 12-byte outer STR record envelope. Its little-endian length at record +0x04 measures the body beginning at record +0x0C. The following table uses that body start as zero. The complete-body layout is the input expected by SimGroup.cs; the leading zero word is part of this body, not evidence of a 0x1607 asset subheader.

Header offsets in a complete body and a legacy BMS dump

0x00 Omitted UInt32 BE Opaque word 0 Zero in the inspected US records; meaning unassigned.
0x04 0x00 UInt32 BE Opaque word 1 Zero in the inspected US records; meaning unassigned.
0x08 0x04 Byte[4] Magic 53 69 6D 47, ASCII SimG.
0x0C 0x08 UInt32 BE Version 1 in the inspected samples.
0x10 0x0C UInt32 BE GUID32 Group identifier used by the viewer. A filename-hash algorithm is not established; zero identifiers occur in the EU outputs.
0x14 0x10 UInt32 BE Flags Read by the viewer; bit meanings are unresolved.
0x18 0x14 UInt32 BE nEnts Number of entity packets followed by the viewer.
0x1C 0x18 UInt32 BE nEntsDispatched Viewer field name; runtime meaning is unverified.
0x20 0x1C UInt32 BE SharedDataSize Viewer field name; the associated region and use require further analysis.
0x24 0x20 UInt32 BE DictionarySize Viewer field name; dictionary semantics are unresolved.
0x28 0x24 UInt32 BE ppEntPackets Body-absolute offset to a UInt32 BE containing the body-absolute entity-array offset. Value 0x30 in all 452 inspected US records.

Pointer bases: read pEntPackets = BE32(body[ppEntPackets]), then start at body[pEntPackets]. In a legacy DAT, both stored absolute pointer values still use the complete-body base: access the pointer word at ppEntPackets - 4 and the entity array at pEntPackets - 4. Field-relative references do not need that subtraction. A legacy file may also contain later record envelopes, so its total length is not a reliable first-body length.

US zone06 example: source ps3-us:PS3_GAME/USRDIR/loc/loc/zone06.str, section 3, record offset 0x660. Its complete body is 244 bytes; the corresponding legacy output was 240 bytes. SimG moves from legacy +4 to complete-body +8, and the viewer's pointer base is preserved. The group identifier is 0x64AC1B75, nEnts = 1, ppEntPackets = 0x30 and pEntPackets = 0xC0.

Entity Entry

The following offsets are relative to one entity packet, after resolving the body-absolute entity-array pointer. Field names and traversal follow SimGroup.cs; the fixed opaque regions are retained without assigning runtime meanings.

Packet offset Type Name Interpretation
0x00 Byte[16] Opaque prefix Skipped by the viewer.
0x10 UInt8 nAttrHandlerFlags Attribute-handler flags; semantics unresolved.
0x11 UInt8 SpawnMask The viewer activates the object when this equals 1. That condition is tool behavior, not a complete runtime spawn specification.
0x12 UInt8 nAttachedRes Count of attached-resource references.
0x13 UInt8 nAttrPackets Count of attribute-packet references.
0x14 Byte[4] Opaque word Skipped by the viewer.
0x18 Int32 BE GUIDOffset Signed offset from this field's own address to a 16-byte entity GUID, read as four UInt32 BE words.
0x1C UInt32 BE BehaviorID Behavior identifier used by the viewer.
0x20 Int32 BE[nAttachedRes] Attached-resource references Each signed reference is relative to its own four-byte field and targets a four-word GUID128.
0x20 + 4*nAttachedRes Int32 BE[nAttrPackets] Attribute-packet references Each signed reference is relative to its own field and targets an attribute packet.

The viewer advances to the next entity packet at packet_start + 0x20 + 4*(nAttachedRes + nAttrPackets). All 416 legacy EU files carrying SimG at +4 could be traversed for their first body's entity GUIDs using this rule and the corrected absolute pointer base. This check did not enumerate additional SimGroups hidden later in those legacy files.

Attribute packets

The viewer reads a UInt32 BE handler identifier at attribute-packet +0 and a UInt16 BE attribute count at +4. It then reads a 16-bit mask, or a 32-bit mask when the count exceeds 16, and aligns the following slots to four bytes. SimGroup.cs uses the ordinary little-endian BinaryReader.ReadUInt16/ReadUInt32 calls for this mask, unlike its surrounding big-endian reads. This is attributed implementation evidence; mask byte order and wider-count behavior need direct validation.

For each attribute index whose mask bit is clear, that parser retains one four-byte slot. Handler code interprets individual slots as integers, floats or signed field-relative references. It does not demonstrate that every stored slot is an integer, that set mask bits mean “active,” or that all handlers and default-value rules are understood.

Separate UIE payloads

UIE is an observed STR metadata resource-type string. No acronym expansion is established. These resources are embedded assets of type 0x1607, not SimGroup 0x2207 bodies, and have no SimG signature in the inspected prefixes. They received numbered DAT names because their metadata path was empty.

The inspected US ps3-us:PS3_GAME/USRDIR/loc/loc.str asset occurs in section 6 at decompressed record offset 0x683D8: object name World, resource type UIE, empty file path, 72-byte metadata subheader and 60-byte payload. The corrected extraction retains those same 60 payload bytes. The separate legacy EU L01_LandOfChocolate/loc_str/00000020.dat sample also contains three 20-byte entries; its historical output path alone does not verify original EU archive membership.

Observed repeating 20-byte UIE entries
Entry offset Type Observation
0x00 UInt32 LE Key. Keys are strictly ascending and unique within each of the 18 inspected EU payloads.
0x04 UInt32 LE[4] Four-word GUID value. Convert each word's byte order before comparing with a SimGroup GUID serialized as four UInt32 BE words.

All 18 EU non-SimGroup payload sizes are multiples of 20, ranging from 40 to 6,160 bytes and totaling 1,125 entries. The first GUID word is constant within each payload and differs between levels. Comparing the four little-endian words against parsed first-body SimGroup entity GUIDs from the same extracted level matched 1,106 entries; comparing the raw 16 bytes matched none.

Every list includes key 0x0CC92646. The viewer's lowercase SDBM implementation hashes its known label ZoneWorld to this value, and each of the 18 corresponding GUIDs matched a main-stream entity with behavior ID 0x0CC92646. The other matched keys differ from their target entity behavior IDs, so the key is not generally a behavior/class identifier. A label-to-entity index is a supported hypothesis; the complete naming namespace and runtime lookup algorithm are unverified.

Key 0x4561376A remains unmatched in all 18 lists; Bartman additionally has unmatched key 0xD1382DA6. No label for either key was established. The comparison covered first-body entities in the available legacy DATs, which could contain additional concatenated records; it does not prove that these GUIDs are absent from the original game, refer to another resource family, or are created dynamically.
