.STR Archive Structure (EA Stream File)

Version: 1.0
Last Updated: 2026-10-02
Author(s): samarixum

The .str file is EA's streaming container format used by the RenderWare engine on PS3/Xbox 360. It contains a metadata header, a section-descriptor array, and aligned section payloads. In this repository, operations/simpsons_str.bms is the practical extraction reference: it uses QuickBMS comtype dk2 for EA RefPack sections and parses embedded records sequentially.

Endianness: The file header and section descriptors are big-endian. Embedded asset records are mixed-endian: the outer chunk-size word is read as little-endian by the C++ prototype, while header sizes, string lengths, and payload sizes are read as big-endian. The QuickBMS script discards the outer chunk-size word rather than interpreting it.

Parsing Algorithm Overview

  1. Read and validate file header at offset 0x00
  2. Navigate to StreamFile struct at header offset pStreamFile
  3. Navigate to Section array at header offset pSectionArr
  4. For each section:
    1. Read section descriptor (6 × UInt32)
    2. Read the section payload using its compressed and decompressed sizes.
    3. If the payload begins with RefPack signature 0x10FB, decompress it with QuickBMS dk2.
    4. Walk embedded records in order using each record's HeaderSize and aligned payload size; a zero HeaderSize is treated as remaining raw section data.

File Header Structure

Located at offset 0x00. Size: 20 bytes (0x14).

Section Descriptor Array

Located at file offset = header.pSectionArr. Array of nSections entries, each 24 bytes.

To parse: For i = 0 to nSections-1, seek to (pSectionArr + i*24) and read 24 bytes.

To parse: For i = 0 to nSections-1, seek to pSectionArr + i*24 and read 24 bytes. The QuickBMS script computes the first section-data position by aligning the end of the header and descriptor array up to 0x800, then advances by each section's stored size.

Section Data Decompression

The QuickBMS script reads the section table at pSectionArr (the big-endian pointer at file offset 0x10). It checks the first two bytes of each section payload for 10 FB; when present, clog with dk2 expands ReadSize bytes to DataSize. Otherwise the section bytes are copied as raw data. This describes the script's behavior and is distinct from interpreting the section's CompressorID alone.

The 20-byte core header is followed by eight additional UInt32 values that QuickBMS reads but does not interpret, bringing its fixed preamble to 0x34 bytes. Their individual meanings are not established here.

StreamFile Struct

Located at file offset = header.pStreamFile. Size: ~48+ bytes (variable due to string).

Section Descriptor Array

Located at file offset = header.pSectionArr. Array of nSections entries, each 24 bytes.

To parse: For i = 0 to nSections-1, seek to pSectionArr + i*24 and read 24 bytes. The QuickBMS script computes its section-data base from the 0x34-byte fixed preamble plus nSections * 24, then rounds that position up to a 0x800 boundary. It advances from the aligned base by each section's stored size; in the standard layout, section data begins at 0x800.

Offset (Rel) Size Type Name Description
0x00 4 UInt32 BE MemPolicyID Memory allocation policy. Informational; typically 0.
0x04 4 UInt32 BE CompressorID Critical: Determines if section data is compressed.
  • 0xB9F0B9EC = Refpack compression
  • 0x0EAC15C8 = Uncompressed (raw data)
0x08 4 Int32 BE DataSize Critical: Size of decompressed data (or raw data if uncompressed). Use this to allocate buffer or validate size.
0x0C 4 Int32 BE AllocSize Size to reserve in memory. Typically ≥ DataSize. May include padding.
0x10 4 Int32 BE ReadSize Critical: Amount of bytes to read from disk. If CompressorID is Refpack, this is compressed size; otherwise equals DataSize.
0x14 4 Int32 BE ReadOffset Critical: Absolute file offset where section data begins. Seek here before reading ReadSize bytes.

Section Data Decompression

Algorithm:

  1. Seek to file offset = ReadOffset
  2. Read ReadSize bytes into a buffer
  3. If CompressorID == 0xB9F0B9EC:
    • Decompress using Refpack algorithm. Output buffer size should be DataSize.
    • Validate: decompressed output must be exactly DataSize bytes.
  4. If CompressorID == 0x0EAC15C8:
    • Data is uncompressed; use buffer directly (which has ReadSize == DataSize).
  5. If CompressorID is any other value:
    • Can attempt to treat as uncompressed, or abort with error.

Chunk Scanning and Parsing

After section decompression/acquisition, the QuickBMS script walks records sequentially. The first four bytes contain a two-byte type identifier and two-byte padding; the following fields include the record version and HeaderSize. The common 0x1607 embedded-asset record has the layout below. Do not treat the C++ prototype's 0x1607-only loop as a complete section scanner.

Record-walking algorithm:

  1. Start at offset zero in the decompressed section.
  2. Read the 16-byte outer record header, including the big-endian HeaderSize at offset 0x0C.
  3. If HeaderSize is zero, treat the remaining section bytes after the outer header as raw headerless data.
  4. Otherwise read the variable metadata subheader, then locate the payload at record_start + 0x10 + HeaderSize.
  5. Use the subheader's PayloadSize for the exact data length; advance to the next record after rounding that length up to a four-byte boundary.

Embedded Asset Chunk (0x1607)

Location: Within decompressed section data. The QuickBMS script reads a 16-byte record header, then either handles a headerless record or parses a variable-length metadata subheader.

Outer Record Header (16 bytes)

Offset (relative) Size Type Name Description
0x00 2 UInt16 BE ChunkType 0x1607 for an embedded asset record (bytes 16 07).
0x02 2 UInt16 BE Padding Observed as 0x0000.
0x04 4 UInt32 LE* ChunkSize The C++ prototype reads this as little-endian and computes the record end from chunk_start + 0x0C + ChunkSize. QuickBMS reads but discards this word; its byte order and exact scope are therefore a prototype-derived interpretation.
0x08 4 UInt32 ChunkVersion Stream/version stamp or reserved value; QuickBMS discards it and the prototype skips it.
0x0C 4 UInt32 BE HeaderSize Byte length of the metadata subheader beginning at 0x10. When zero, QuickBMS treats the remaining section bytes after this outer header as a headerless payload.

*ChunkSize interpretation: In the prototype's model, ChunkSize = 4 + HeaderSize + align4(PayloadSize), where the first four bytes are the HeaderSize field and align4(n) = (n + 3) & ~3. QuickBMS does not use this field; verify this relationship against additional samples before treating it as a normative invariant.

Metadata Sub-Header (HeaderSize bytes)

The following fields occur sequentially in the subheader. Each string is preceded by a big-endian UInt32 byte length. In observed data, string contents include their null terminator and any 0xBF fill bytes used to reach a four-byte boundary. For example, an empty four-byte string field has length 4 followed by 00 BF BF BF; those four content bytes are not the length value.

Sequence Size Type Name Description
1 4 + variable UInt32 BE + Byte[] ObjectNameLen, ObjectName Length-prefixed internal object/symbol name. Often an empty placeholder for texture dictionaries.
2 16 Byte[16] AssetMeta Fixed metadata block between the first and second strings.
3 4 + variable UInt32 BE + Byte[] TypeNameLen, TypeName Length-prefixed resource type, for example rwID_TEXDICTIONARY or GRAPH, followed by null/padding bytes.
4 4 + variable UInt32 BE + Byte[] FilePathLen, FilePath Length-prefixed output path/name. This third string is the actual resource path used by QuickBMS, not the first internal object name.
5 4 + ExtraLen UInt32 BE + Byte[] ExtraLen, ExtraData Length-prefixed type-specific parameters.
6 4 UInt32 BE ReservedZero Observed as zero.
7 4 UInt32 BE PayloadSize Exact unpadded length of the binary asset payload.

Asset Payload and Record Boundary

The asset payload begins at chunk_start + 0x10 + HeaderSize and contains exactly PayloadSize bytes. The next record begins after the payload rounded up to a four-byte boundary: payload_start + ((PayloadSize + 3) & ~3). The QuickBMS script applies this four-byte alignment when advancing to the next record.

If HeaderSize == 0, QuickBMS instead treats bytes from chunk_start + 0x10 through the end of that decompressed section as raw headerless data and uses an empty output name.

Parsing pseudocode:


record_start = current_section_offset
while record_start < section_size:
    chunk_type = read_u16_be(record_start)
    padding = read_u16_be(record_start + 2)
    chunk_size = read_u32_le(record_start + 4)  // Prototype interpretation; QuickBMS ignores it
    chunk_version = read_u32(record_start + 8)
    header_size = read_u32_be(record_start + 0x0C)

    if header_size == 0:
        payload_start = record_start + 0x10
        payload_size = section_size - payload_start
        export_raw_payload(name = "", offset = payload_start, size = payload_size)
        break

    subheader = record_start + 0x10
    object_name = read_length_prefixed_string_be(subheader)
    asset_meta = read_bytes(16)
    type_name = read_length_prefixed_string_be()
    file_path = read_length_prefixed_string_be()
    extra_data = read_length_prefixed_bytes_be()
    reserved_zero = read_u32_be()
    payload_size = read_u32_be()

    payload_start = record_start + 0x10 + header_size
    export_payload(file_path, payload_start, payload_size)
    record_start = payload_start + ((payload_size + 3) & ~3)

RefPack Stream (QuickBMS dk2)

The section extraction script selects RefPack decompression when the section begins with signature 0x10FB, then passes the compressed byte count and expected decompressed size to QuickBMS clog. The command details below are transcribed from Str_Load_Full::UnCompressSection; QuickBMS dk2 remains the working decoder.

Stream element Encoding Description
Signature UInt16 BE 0x10FB. The C++ prototype checks bit 0x0100; when set (for example 0x11FB), it reads an additional UInt24 BE compressed-size field. QuickBMS checks specifically for 0x10FB.
Optional compressed size UInt24 BE Present in the prototype when signature bit 0x0100 is set. The prototype reads but does not otherwise use this value.
Decompressed size UInt24 BE Expected output size for the RefPack stream.

Each command starts with byte0. The first matching condition below determines the command form:

Condition Command bytes Literal bytes before back-reference Back-reference length Backward distance
(byte0 & 0x80) == 0 2 byte0 & 0x03 ((byte0 >> 2) & 0x07) + 3 ((byte0 & 0x60) << 3) + byte1 + 1
(byte0 & 0xC0) == 0x80 3 byte1 >> 6 (byte0 & 0x3F) + 4 ((byte1 & 0x3F) << 8) + byte2 + 1
(byte0 & 0xE0) == 0xC0 4 byte0 & 0x03 ((byte0 & 0x0C) << 6) + byte3 + 5 ((byte0 & 0x10) << 12) + (byte1 << 8) + byte2 + 1

When (byte0 & 0xE0) == 0xE0, the command is a literal block or terminator. Compute literal_count = (byte0 & 0x1F) * 4 + 4. If the result is at most 0x70, copy that many literal bytes. Otherwise, copy byte0 & 0x03 trailing literal bytes and end decompression.

Extraction Reference and C++ Prototype Caveats

Use operations/simpsons_str.bms with QuickBMS as the extraction reference. The C++ files under reversing/TheSimpsonsGameFileExtractor-main/project/Source are an unfinished prototype, not an equivalent parser:

  • Str_Load::CheckHeaderForCompression hardcodes section descriptors at offset 0x14; Str_Load_Full reads the pointer at 0x10 but still hardcodes the data start at 0x800.
  • Both IsStrFile implementations compare std::string::compare to 1, rather than accepting 0 for equal strings.
  • The C++ asset parser reads only two of the three length-prefixed strings and does not use the third string containing the actual file path. Its StringIndexes helper returns an empty string if the internal name has no dot and can retain null/0xBF padding.
  • ExtractSection stops at the first record whose type is not 0x1607, potentially discarding later section data.
  • The prototype writes intermediate section files and later traverses a directory iterator, whose order is unspecified; this can lose the original section order.

Summary: Parsing Workflow

  1. Validate magic: Read header, verify "SToc"
  2. Read header fields: nSections, pStreamFile, pSectionArr
  3. Iterate sections:
    1. Seek to section descriptor at (pSectionArr + i*24)
    2. Read descriptor (MemPolicyID, CompressorID, DataSize, AllocSize, ReadSize, ReadOffset)
    3. Seek to ReadOffset, read ReadSize bytes
    4. If Refpack: decompress to DataSize bytes
    5. If uncompressed: use buffer as-is
  4. Walk decompressed section records:
    1. Test the section start for the RefPack signature and decompress with QuickBMS dk2 when present.
    2. Read each record header in sequence; parse nonzero-HeaderSize records and emit the declared payload path/size.
    3. For HeaderSize == 0, emit the remaining section bytes as a headerless payload.
  5. Validate and store results: Build list of extracted resources (filenames, types, binary data)
