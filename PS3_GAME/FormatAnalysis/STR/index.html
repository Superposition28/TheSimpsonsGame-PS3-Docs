Evidence and limitations

The registered QuickBMS script is the extraction reference. On 2026-10-19, an independent Python RefPack decoder and bounded record walker inspected all 490 STRs (1,193,330,688 source bytes) in the supplementary PS3 US source set. All 2,725 sections and 26,379 record boundaries validated: 25,927 records of type 0x1607 and 452 of type 0x2207. No other outer record types occurred in this source set. Of those sections, 2,473 were RefPack compressed. This is structural coverage of this snapshot, not complete payload or runtime decoding. Source hashes, identification prefixes, sample comparisons and the separate EU output inventory are recorded in the evidence ledger.

Detailed field tables and retained samples are research evidence. Implementation-derived observations must remain attributed to their tools; tentative, observed and contextual relationships do not establish complete original runtime behavior. Offsets in the added tables are zero-based; range ends are exclusive unless stated otherwise.

The .str file is EA's streaming container format used by the RenderWare engine on PS3/Xbox 360. It contains a metadata header, a section-descriptor array, and aligned section payloads. In this repository, operations/simpsons_str.bms is the practical extraction reference: it uses QuickBMS comtype dk2 for EA RefPack sections and parses embedded records sequentially.

Endianness: The file header and section descriptors are big-endian. Record framing is mixed-endian: the outer body-size word is little-endian, while asset header sizes, string lengths and payload sizes are big-endian. This size interpretation matches every record boundary in the audited US source; the updated QuickBMS script uses it. Payload byte orders remain format-specific.

Unnamed payloads and generated DAT names

A numeric xxxxxxxx.dat is an extractor-generated name, not a pathname recovered from the STR. QuickBMS 0.12.0 documents that log "" OFFSET SIZE assigns a sequential hexadecimal number and guesses an extension. Its 64-bit build emitted 16-digit names in the manual runs; existing processed outputs use eight digits. The sequence depends on extraction order, and collision/rename options can change disk names on reruns. The exact cause of a particular historical collision cannot be recovered from its filename alone.

The old script reached an empty name in two different ways:

  1. 0x2207 SimGroup records do not have the 0x1607 asset pathname header. Their first body word is zero in the audited source. The old script mistook this for a zero asset-header length, removed that word, and dumped everything from record +0x10 to the end of the section. This shifted the SimGroup body base by four bytes and could include later record envelopes and assets.
  2. Some 0x1607 records have a real metadata header whose third string (pathname) is empty. All 18 such assets in the audited US source declare resource type UIE; they are distinct from SimGroups. Their exact payload lengths are still declared by their asset metadata.

The existing processed EU tree, locally named GameFiles/1PS3-EU-Full-audio_reorg-isRenamed, contains 434 numeric DAT files: 416 begin with 00 00 00 00 53 69 6D 47 (SimG at legacy output +4), and 18 have a different 20-byte-entry structure. This is an inventory of old outputs, not a new EU extraction; a single old SimG DAT can contain several records. See the separate UIE structure and the full-body versus legacy SimGroup offsets.

Parsing Algorithm Overview

  1. Read and validate file header at offset 0x00
  2. The StreamFile structure is additional research metadata; the registered BMS extractor does not need to interpret it.
  3. Navigate to Section array at header offset pSectionArr
  4. For each section:
    1. Read section descriptor (6 × UInt32)
    2. Read the section payload using its compressed and decompressed sizes.
    3. If the payload begins with RefPack signature 0x10FB, decompress it with QuickBMS dk2.
    4. Walk 12-byte record envelopes using the little-endian body size. Parse asset metadata only for 0x1607; retain other record bodies separately and continue to the declared next boundary.

File Header Structure

Located at offset 0x00. Size: 20 bytes (0x14).

Offset Size Type Name Description
0x00 4 Char[4] Magic Must be SToc (0x53546F63 BE). If not, abort parsing.
0x04 4 UInt32 BE Version Observed as 0x00000007 in all 490 audited US STRs. Other versions require separate validation.
0x08 1 UInt8 nSections Number of Section Descriptor entries. Zero is valid in 18 audited US placeholder streams; do not impose the historical 1–4 assumption.
0x09 1 UInt8 PlatformID Platform-associated byte, observed as 0x06 in all audited US STRs. The old suggested PS3 value 0x07 was not observed.
0x0A 2 Byte[2] Padding Unused, typically 0x00.
0x0C 4 Int32 BE pStreamFile Optional absolute offset to StreamFile metadata. In the US audit this is zero in 450 files and 0x14 in 40; do not dereference a zero pointer.
0x10 4 Int32 BE pSectionArr Absolute offset to the section-descriptor array. It is 0x14 when optional StreamFile metadata is absent; otherwise it follows that metadata. Validate the entire array against the file size.

The core header is 20 bytes. The old QuickBMS script read eight further words unconditionally, often reading into descriptors rather than a separate fixed preamble. The updated script follows pSectionArr; optional StreamFile metadata must be distinguished from the descriptor array.

StreamFile Struct

Located at file offset = header.pStreamFile. Size: ~48+ bytes (variable due to string).

Offset (Rel) Size Type Name Description
0x00 4 UInt32 BE GUID Candidate stream identifier. A filename/hash relationship must be verified per sample; it is not interpreted by the registered BMS script.
0x04 4 Int32 BE pFileName Relative pointer to null-terminated filename string. Add current offset (0x04) to this value, then seek to read until null byte.
0x08 1 UInt8 nParents Number of parent/dependency stream files. Usually 0 or 1.
0x09 1 UInt8 nForceLoad Flags for force-load behavior. Typically 0.
0x0A 1 UInt8 nSections Duplicate of header.nSections. Verify consistency.
0x0B 1 UInt8 Flags Bitfield (flags). Meaning context-dependent.
0x0C 4 Int32 BE Unk Unknown/reserved field. Typically 0.
0x10 4 Int32 BE pRelatives Offset to related stream info. Often 0 (none).
0x14 4 Int32 BE pSectionInfo Offset to additional section metadata. Often 0 (none).

Section Descriptor Array

Located at file offset = header.pSectionArr. Array of nSections entries, each 24 bytes.

To parse: For i = 0 to nSections-1, seek to pSectionArr + i*24 and read 24 bytes. The updated QuickBMS script computes the section-data base as align2048(pSectionArr + nSections * 24). It advances from the aligned base by each section's stored size; in the standard layout, section data begins at 0x800.

Offset (Rel) Size Type Name Description
0x00 4 UInt32 BE MemPolicyID Memory allocation policy. Informational; typically 0.
0x04 4 UInt32 BE CompressorID Candidate compressor identifier from the research prototype; the registered BMS script instead checks the payload signature.
  • 0xB9F0B9EC = Refpack compression
  • 0x0EAC15C8 = Uncompressed (raw data)
0x08 4 Int32 BE DataSize Critical: Size of decompressed data (or raw data if uncompressed). Use this to allocate buffer or validate size.
0x0C 4 Int32 BE AllocSize Size to reserve in memory. Typically ≥ DataSize. May include padding.
0x10 4 Int32 BE ReadSize Critical: Stored section span used to advance to the next section. Includes disk padding: for the raw US zone06 final section it is 0x800, while DataSize is only 0x760. For compressed sections it bounds the RefPack stream; the stream can terminate before this span ends.
0x14 4 Int32 BE UnknownWord The former name ReadOffset was incorrect for the audited US files. It is zero for raw sample sections and is not their absolute file offset. The working extractor reads but does not interpret it. Section positions are derived by accumulating stored spans from the aligned data base.

Section Data Decompression

Algorithm:

  1. Start at the aligned section-data base; each next source offset is the previous offset plus its stored span (ReadSize). Do not use descriptor +0x14 as a source offset.
  2. Read ReadSize bytes into a buffer
  3. If CompressorID == 0xB9F0B9EC:
    • Decompress using Refpack algorithm. Output buffer size should be DataSize.
    • Validate: decompressed output must be exactly DataSize bytes.
  4. If CompressorID == 0x0EAC15C8:
    • Data is uncompressed; use exactly DataSize bytes. ReadSize can include extra padding.
  5. If CompressorID is any other value:
    • Retain the unknown compressor ID and require separate validation. The working script selects decompression by the observed payload signature, rather than this word alone.

Chunk Scanning and Parsing

After section decompression/acquisition, walk bounded records rather than scanning for magic inside payloads. The common envelope is 12 bytes: type/padding at +0, little-endian body size at +4, and an opaque four-byte version stamp at +8. Record end is record_start + 12 + body_size. This end must stay within the uncompressed DataSize; stored disk padding is not a record.

  1. Start at section offset zero and require at least 12 bytes for the envelope.
  2. Read type and body size, validate the end, and preserve source coordinates.
  3. For 0x1607 with a nonzero metadata-header length, parse the asset subheader below and validate its aligned payload end against the outer body size.
  4. For 0x2207, test for SimG at body +8; preserve the complete body. An unrecognized type or zero-header asset is retained as its own opaque body.
  5. Continue at the declared record end, including after a SimGroup. Do not replace an unknown length with the remaining section length.

Known Chunk Types

Type ID Hex Name Size Field Handling Notes
0x10FB 0x10, 0xFB Refpack Compressed Data RefPack stream header Section data may begin with the big-endian signature 0x10FB; QuickBMS invokes dk2 to decompress the section. The stream header and command formats are described below.
0x1607 0x16, 0x07 Embedded Asset 16-byte outer record header, then a variable subheader Common embedded asset record. The subheader contains an internal object name, 16 bytes of metadata, a resource type, a file path, extra data, and the exact payload size. See the detailed layout below.
0x2207 0x22, 0x07 SimGroup UInt32 LE at +4, excluding envelope Simulation group: no asset-path metadata. All 452 audited US bodies have two initial zero words then SimG at +8. Multiple groups and intervening asset records can share one section. See SimGroup / unnamed DAT payloads.
0x2307 0x23, 0x07 Embedded Asset (Compact) Record-specific This label comes from the inspected C# viewer, which throws NotImplementedException for it. None occurred in the audited US set. The BMS preserves its declared body as an opaque record; semantic parsing remains unimplemented.

Embedded Asset Chunk (0x1607)

Location: Within decompressed section data. This record has the common 12-byte envelope followed by a big-endian metadata-header length. Only for this asset type does it make sense to group those fields as the following 16-byte header.

Outer Record Header (16 bytes)

Offset (relative) Size Type Name Description
0x00 2 UInt16 BE ChunkType 0x1607 for an embedded asset record (bytes 16 07).
0x02 2 UInt16 BE Padding Observed as 0x0000.
0x04 4 UInt32 LE* ChunkSize Little-endian body byte count, excluding the 12-byte envelope. Record end is chunk_start + 0x0C + ChunkSize; the updated QuickBMS script uses this observed boundary.
0x08 4 UInt32 ChunkVersion Opaque stream/version stamp; the sample bytes are FF FF 02 18. It is not interpreted by the extractor.
0x0C 4 UInt32 BE HeaderSize Big-endian byte length of the metadata subheader beginning at 0x10. Zero is not permission to dump the section tail: preserve this record body as opaque. The same word position in a different outer type is not necessarily a header length.

*ChunkSize interpretation: ChunkSize = 4 + HeaderSize + align4(PayloadSize), where the first four bytes are the HeaderSize field and align4(n) = (n + 3) & ~3. This relationship validated for all 25,927 audited US asset records and is checked by the updated BMS. Retain separate scope for other builds.

Metadata Sub-Header (HeaderSize bytes)

The following fields occur sequentially in the subheader. Each string is preceded by a big-endian UInt32 byte length. In observed data, string contents include their null terminator and any 0xBF fill bytes used to reach a four-byte boundary. For example, an empty four-byte string field has length 4 followed by 00 BF BF BF; those four content bytes are not the length value.

Sequence Size Type Name Description
1 4 + variable UInt32 BE + Byte[] ObjectNameLen, ObjectName Length-prefixed internal object/symbol name. Often an empty placeholder for texture dictionaries.
2 16 Byte[16] AssetMeta Fixed metadata block between the first and second strings.
3 4 + variable UInt32 BE + Byte[] TypeNameLen, TypeName Length-prefixed resource type, for example rwID_TEXDICTIONARY or GRAPH, followed by null/padding bytes.
4 4 + variable UInt32 BE + Byte[] FilePathLen, FilePath Length-prefixed output path/name. This third string is the resource path used by QuickBMS, rather than the first object name. It can be empty: all 18 unnamed US asset records have resource type UIE and object name World.
5 4 + ExtraLen UInt32 BE + Byte[] ExtraLen, ExtraData Length-prefixed type-specific parameters.
6 4 UInt32 BE ReservedZero Observed as zero.
7 4 UInt32 BE PayloadSize Exact unpadded length of the binary asset payload.

Asset Payload and Record Boundary

The asset payload begins at chunk_start + 0x10 + HeaderSize and contains exactly PayloadSize bytes. The next record begins after the payload rounded up to a four-byte boundary: payload_start + ((PayloadSize + 3) & ~3). The QuickBMS script applies this four-byte alignment when advancing to the next record.

The old HeaderSize == 0 branch removed a body word and dumped the section tail under an empty name. That behavior is obsolete; see the two distinct unnamed-output cases.

Parsing pseudocode:


record_start = 0
while record_start < section_size:
    require(section_size - record_start >= 12)
    chunk_type = read_u16_be(record_start)
    body_size = read_u32_le(record_start + 4)
    body_start = record_start + 12
    record_end = body_start + body_size
    require(record_end <= section_size)

    if chunk_type == 0x1607 and read_u32_be(body_start) > 0:
        header_size = read_u32_be(body_start)
        subheader = body_start + 4
        object_name = read_length_prefixed_string_be(subheader)
        asset_meta = read_bytes(16)
        type_name = read_length_prefixed_string_be()
        file_path = read_length_prefixed_string_be()  // Can be empty
        extra_data = read_length_prefixed_bytes_be()
        reserved_zero = read_u32_be()
        payload_size = read_u32_be()
        payload_start = body_start + 4 + header_size
        require(payload_start + align4(payload_size) == record_end)
        export_asset(file_path, type_name, payload_start, payload_size)
    else:
        // Includes complete SimGroup bodies and unparsed record types
        export_record_body(chunk_type, body_start, body_size)

    record_start = record_end

RefPack Stream (QuickBMS dk2)

The section extraction script selects RefPack decompression when the section begins with signature 0x10FB, then passes the compressed byte count and expected decompressed size to QuickBMS clog. The command details below are transcribed from Str_Load_Full::UnCompressSection; QuickBMS dk2 remains the working decoder.

Stream element Encoding Description
Signature UInt16 BE 0x10FB. The C++ prototype checks bit 0x0100; when set (for example 0x11FB), it reads an additional UInt24 BE compressed-size field. QuickBMS checks specifically for 0x10FB.
Optional compressed size UInt24 BE Present in the prototype when signature bit 0x0100 is set. The prototype reads but does not otherwise use this value.
Decompressed size UInt24 BE Expected output size for the RefPack stream.

Each command starts with byte0. The first matching condition below determines the command form:

Condition Command bytes Literal bytes before back-reference Back-reference length Backward distance
(byte0 & 0x80) == 0 2 byte0 & 0x03 ((byte0 >> 2) & 0x07) + 3 ((byte0 & 0x60) << 3) + byte1 + 1
(byte0 & 0xC0) == 0x80 3 byte1 >> 6 (byte0 & 0x3F) + 4 ((byte1 & 0x3F) << 8) + byte2 + 1
(byte0 & 0xE0) == 0xC0 4 byte0 & 0x03 ((byte0 & 0x0C) << 6) + byte3 + 5 ((byte0 & 0x10) << 12) + (byte1 << 8) + byte2 + 1

When (byte0 & 0xE0) == 0xE0, the command is a literal block or terminator. Compute literal_count = (byte0 & 0x1F) * 4 + 4. If the result is at most 0x70, copy that many literal bytes. Otherwise, copy byte0 & 0x03 trailing literal bytes and end decompression.

Extraction Reference and C++ Prototype Caveats

Use operations/simpsons_str.bms with QuickBMS as the extraction reference. The C++ files under reversing/TheSimpsonsGameFileExtractor-main/project/Source are an unfinished prototype, not an equivalent parser:

  • Str_Load::CheckHeaderForCompression hardcodes section descriptors at offset 0x14; Str_Load_Full reads the pointer at 0x10 but still hardcodes the data start at 0x800.
  • Both IsStrFile implementations compare std::string::compare to 1, rather than accepting 0 for equal strings.
  • The C++ asset parser reads only two of the three length-prefixed strings and does not use the third string containing the actual file path. Its StringIndexes helper returns an empty string if the internal name has no dot and can retain null/0xBF padding.
  • ExtractSection stops at the first record whose type is not 0x1607, potentially discarding later section data.
  • The prototype writes intermediate section files and later traverses a directory iterator, whose order is unspecified; this can lose the original section order.

Summary: Parsing Workflow

  1. Validate magic: Read header, verify "SToc"
  2. Read header fields: nSections, pStreamFile, pSectionArr
  3. Iterate sections:
    1. Seek to section descriptor at (pSectionArr + i*24)
    2. Read descriptor (MemPolicyID, CompressorID, DataSize, AllocSize, ReadSize, UnknownWord)
    3. Read at the accumulated source section offset; advance that offset by ReadSize
    4. If Refpack: decompress to DataSize bytes
    5. If uncompressed: use buffer as-is
  4. Walk decompressed section records:
    1. Test the section start for the RefPack signature and decompress with QuickBMS dk2 when present.
    2. Read each 12-byte envelope; validate the little-endian body size. For 0x1607 parse its asset metadata and emit the exact payload.
    3. Preserve each 0x2207 SimGroup or unparsed record body separately, then continue at its declared end. Empty asset paths receive an explicit synthetic name in the extraction tool.
  5. Validate and store results: Build list of extracted resources (filenames, types, binary data)
