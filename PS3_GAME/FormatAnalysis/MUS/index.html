Simpsons Game .mus Audio Format

File Extension: .mus

Origin: The Simpsons Game (PAL PS3 Version), likely a proprietary format from EA Redwood Shores.

Purpose: Container archives for Interactive, Segmented, and Layered background music.

Key Characteristics:

  • Proprietary EA Format Container:
  • Two Subtypes: Identified by values in the header:
    • Type 1: Header bytes 0x08-0x0B = 0F 00 00 00 (15 LE), bytes 0x0C-0x0F = 78 01 32 00.
    • Type 2: Header bytes 0x08-0x0B = 0B 00 00 00 (11 LE), bytes 0x0C-0x0F = 02 03 02 03.
  • Header and Table of Contents: Contains a per-file ID, a file details header, and structured Table of Contents entries indicating metadata (.snr) and audio stream payload (.sns) locations.
  • Extraction & Decodability: Unpacked successfully via operations/mus.bms into paired .snr and .sns segments, which natively decode into .wav streams using vgmstream.
  • Segmented Streaming Structure: The audio clips are split into contiguous short streams (often approx. 2-second segments) intended to be played consecutively to seamlessly assemble the full song.

<h1>The Simpsons Game (2007) EA <code>.mus</code> Audio Format</h1>

<p><strong>File Extension:</strong> <code>.mus</code></p>
<p><strong>Origin:</strong> The Simpsons Game (PS3/Xbox 360), EA Redwood Shores.</p>
<p><strong>Purpose:</strong> Container archives for interactive, segmented, and layered background music.</p>

<hr>

<h2>1. Verified Facts (What We Know)</h2>
<ul>
    <li><strong>It is an Archive, Not a Flat Stream:</strong> <code>.mus</code> files are not single continuous audio tracks. They are containers holding multiple distinct audio segments (metadata and payload pairs). Treating them as a single raw stream results in completely corrupted static/noise.</li>
    <li><strong>Big-Endian Table of Contents (TOC):</strong> The archive structure relies on a directory/TOC that begins at offset <code>0x28</code>. The total number of files/segments inside the archive is read as a single byte at offset <code>0x04</code> of the header.</li>
    <li><strong>28-Byte Structured TOC Entries:</strong> Each entry in the TOC is <code>28 bytes</code> (<code>0x1C</code>) long and contains the following Big-Endian fields (as parsed in <code>mus.bms</code>):
        <ul>
            <li><code>0x00</code> (uint32): <strong>HASH</strong> (Sound-specific hash identifier)</li>
            <li><code>0x04</code> (uint16): <strong>NUMBER</strong> (Segment stream index/sequence number)</li>
            <li><code>0x06</code> (uint16): <strong>PADDING</strong> (Usually always 0)</li>
            <li><code>0x08</code> (uint32): <strong>SNR_OFFSET_RAW</strong> (The packed pointer to the SNR header. Multiply by <code>0x10</code> to resolve the real file position)</li>
            <li><code>0x0C</code> (uint32): <strong>SNS_OFFSET_RAW</strong> (The packed pointer to the SNS stream body. Multiply by <code>0x80</code> to resolve the real file position)</li>
            <li><code>0x10</code> (uint32): <strong>SNR_SIZE</strong> (Exact size of the SNR metadata payload in bytes)</li>
            <li><code>0x14</code> (uint32): <strong>SNS_SIZE</strong> (Exact size of the SNS stream payload in bytes)</li>
            <li><code>0x18</code> (uint32): <strong>PADDING</strong> (Usually always 0)</li>
        </ul>
    </li>
    <li><strong>Interactive Concat/Sequence Mechanics (~2-Second Snippets):</strong> The audio tracks are split into consecutively numbered contiguous segments. Each pair represents a very short, approx. 2-second piece of background music (complying with EA's interactive music engine). The full song is constructed by programmatically stitching or playing these segments sequentially one after the other.</li>
    <li><strong>EA SNR/SNS Container Behavior:</strong> The archive holds paired components: the <code>.snr</code> containing stream description metadata (sample rate, channels, EA-XAS ADPCM layout) and the matching blocked <code>.sns</code> containing the audio payload.</li>
    <li><strong>VGMStream Integration:</strong> Running <code>vgmstream</code> directly on the extracted <code>.snr</code> file decodes it cleanly into a standard <code>.wav</code> snippet. It reports the codec as <code>Electronic Arts EA-XAS 4-bit ADPCM v1</code> using the <code>Electronic Arts SNR+SNS header</code> metadata layout.</li>
</ul>

<hr>

<h2>2. Background Music Segment Playback & Construction</h2>
<p>Because the tracks are split into numerous ~2-second snippets, reconstruction of a full playable soundtrack requires sequencing. The typical workflow used in the <code>mustest.ps1</code> test script details this behavior:</p>
<ol>
    <li>Unpack the <code>.mus</code> file with <code>operations/mus.bms</code> using QuickBMS to extract all numbered <code>.snr</code> and <code>.sns</code> chunks.</li>
    <li>Invoke <code>vgmstream-cli</code> targeting each <code>.snr</code> file individually, exporting them to independent <code>.wav</code> files.</li>
    <li>Clean up the intermediate raw <code>.snr</code> and <code>.sns</code> segments, leaving only the converted <code>.wav</code> files.</li>
    <li>Stitch the resulting chunks sequentially (e.g., <code>[Filename]__000.wav</code>, then <code>[Filename]__001.wav</code>, and so on) in the engine or media pipeline to reconstruct the full playback.</li>
</ol>
