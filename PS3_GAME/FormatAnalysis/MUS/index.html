Simpsons Game .mus Audio Format

File Extension: .mus

Origin: The Simpsons Game (PS3 & Xbox 360 Versions), proprietary format from EA Redwood Shores.

Purpose: Container archives for Interactive, Segmented, and Layered background music.

Key Characteristics:

  • Proprietary EA Format Container: Shared archive structure and stream inventory across both PS3 and Xbox 360.
  • Two Subtypes: Identified by values in the header:
    • Type 1: Header bytes 0x08-0x0B = 0F 00 00 00 (15 LE), bytes 0x0C-0x0F = 78 01 32 00.
    • Type 2: Header bytes 0x08-0x0B = 0B 00 00 00 (11 LE), bytes 0x0C-0x0F = 02 03 02 03.
  • Header and Table of Contents: Contains a per-file ID, a file details header, and structured Table of Contents entries indicating metadata (.snr) and audio stream payload (.sns) locations.
  • Cross-Platform Extraction & Decodability: Both PS3 and Xbox 360 archives unpack using the exact same QuickBMS script (operations/mus.bms) into paired .snr and .sns segments, and outputs from both platforms natively decode into .wav streams using vgmstream.
  • Segmented Streaming Structure: The audio clips are split into contiguous short streams (often approx. 2-second segments) intended to be played consecutively to seamlessly assemble the full song.

2. Discovery of Header Signatures

Initial notes only documented two subtypes, but analysis across all files reveals four distinct signatures. Notice the pattern in the first byte of the signature sequence:

The "Type 1" Family (Ends in 78 01 32 00):

0F 00 00 00 78 01 32 00 (Known Type 1) - Found in brt_mus, hub_mus, loc_mus, mob_mus, mtp_mus, nvq_mus, rwc_mus, sss_mus.
0E 00 00 00 78 01 32 00 (Variant)      - Found in 80b_mus, gts_mus, menu_mus.

The "Type 2" Family (Ends in 02 03 02 03):

0B 00 00 00 02 03 02 03 (Known Type 2) - Found in bsh_mus, spr_mus, treetemp.mus.
0C 00 00 00 02 03 02 03 (Variant)      - Found in bin.mus, cheater.mus, moh_mus.

What this means: The first byte (0x0F/0x0E or 0x0B/0x0C) is likely a flag or a format version number, while the last 4 bytes are the true "magic number" identifying the encoding algorithm or block structure.

3. The Unknown Integer is a "Cue/Track Count"

The Unk/Size variable at offset 0x04 returns values ranging from 6 (for hub_mus.mus and gts_mus.mus) up to 249 (for nvq_mus.mus).

Because these files are enormous (e.g., nvq_mus.mus is 188 MB but its integer is only 249), this integer is not a file size, byte offset, or total sample count. Since background music uses interactive stems (multiple segments/layers of music fading in and out based on gameplay), this integer represents the number of individual streams, cues, or segments multiplexed into the container.

4. VBR Frame Delimiters Confirmed

Scanning hub_mus.mus showed that the 0C 00 00 00 padding marker appears in 12.47% of the 64-byte chunks.

What this means: If the marker was only used at the very end of the file, it would be 0.001%. Because it appears roughly 1 out of every 8 chunks (100 / 12.47 ≈ 8.01), this strongly supports the theory that this marker denotes the end of logical audio frames. An average audio frame in this format spans about 8 physical chunks (~512 bytes).

1. Verified Archive Structure (What We Know)

  • It is an Archive, Not a Flat Stream: .mus files are not single continuous audio tracks. They are containers holding multiple distinct audio segments (metadata and payload pairs). Treating them as a single raw stream results in corrupted static/noise.
  • Big-Endian Table of Contents (TOC): The archive structure relies on a directory/TOC that begins at offset 0x28. The total number of files/segments inside the archive is read as a single byte at offset 0x04 of the header.
  • 28-Byte Structured TOC Entries: Each entry in the TOC is 28 bytes (0x1C) long and contains the following Big-Endian fields (as parsed in operations/mus.bms on both PS3 and Xbox 360):
    • 0x00 (uint32): HASH (Sound-specific hash identifier)
    • 0x04 (uint16): NUMBER (Segment stream index/sequence number)
    • 0x06 (uint16): PADDING (Usually always 0)
    • 0x08 (uint32): SNR_OFFSET_RAW (The packed pointer to the SNR header. Multiply by 0x10 to resolve the real file position)
    • 0x0C (uint32): SNS_OFFSET_RAW (The packed pointer to the SNS stream body. Multiply by 0x80 to resolve the real file position)
    • 0x10 (uint32): SNR_SIZE (Exact size of the SNR metadata payload in bytes)
    • 0x14 (uint32): SNS_SIZE (Exact size of the SNS stream payload in bytes)
    • 0x18 (uint32): PADDING (Usually always 0)
  • Interactive Concat/Sequence Mechanics (~2-Second Snippets): The audio tracks are split into consecutively numbered contiguous segments. Each pair represents a short, approx. 2-second piece of background music (complying with EA's interactive music engine). The full song is constructed by programmatically stitching or playing these segments sequentially one after the other.
  • EA SNR/SNS Container Behavior: The archive holds paired components: the .snr containing stream description metadata (codec byte, sample rate, channels) and the matching .sns containing the compressed audio payload.
  • VGMStream Integration: Running vgmstream directly on the extracted .snr file from either PS3 or Xbox 360 decodes it cleanly into a standard .wav snippet using the Electronic Arts SNR+SNS header metadata layout.

2. Platform Differences (PS3 vs. Xbox 360)

The .mus archives have the exact same container structure and stream inventory across platforms (for example, bin.mus contains 63 numbered .snr/.sns pairs on both PS3 and Xbox 360). The difference lies strictly in the audio codec used inside those stream pairs:

Comparison of embedded stream bin__000 (from bin.mus) across platforms
Property PS3 Xbox 360
Codec EA-XAS 4-bit ADPCM v1 Xbox Media Audio 2 (XMA2)
Header codec byte 0x04 0x03
Sample rate 48 kHz 48 kHz
Channels 6 6
Samples / duration 153,594 / 3.200 s 153,594 / 3.200 s
Bitrate 1373 kb/s 799 kb/s
.sns payload size 549,376 bytes 319,872 bytes
  • DIFF_BY_PLATFORM Expected: PS3 stores the music segments as EA-XAS 4-bit ADPCM v1 (header codec byte 0x04), while Xbox 360 stores the exact same timed multichannel segments as XMA2 (header codec byte 0x03).
  • File Size Differences: The smaller Xbox 360 .mus file sizes result entirely from its lower-bitrate XMA2 encoding (e.g., 799 kb/s vs. 1373 kb/s), not missing music segments.
  • Unified Pipeline Compatibility: Because the outer .mus TOC layout is identical, operations/mus.bms extracts both PS3 and Xbox 360 archives without modification, and vgmstream automatically detects the .snr codec byte (0x04 or 0x03) to decode both platforms' outputs to .wav.

3. Background Music Segment Playback & Construction

Because the tracks are split into numerous ~2-second snippets, reconstruction of a full playable soundtrack requires sequencing. The typical workflow used in the mustest.ps1 test script details this behavior:

  1. Unpack the .mus file (PS3 or Xbox 360) with operations/mus.bms using QuickBMS to extract all numbered .snr and .sns chunks.
  2. Invoke vgmstream-cli targeting each .snr file individually, exporting them to independent .wav files.
  3. Clean up the intermediate raw .snr and .sns segments, leaving only the converted .wav files.
  4. Stitch the resulting chunks sequentially (e.g., [Filename]__000.wav, then [Filename]__001.wav, and so on) in the engine or media pipeline to reconstruct the full playback.

4. QuickBMS Extraction & vgmstream Verification

  • QuickBMS Extraction Works (PS3 & Xbox 360): The module script operations/mus.bms successfully extracts each .mus archive on both platforms into paired .snr and .sns files.
  • vgmstream Playback Works (PS3 & Xbox 360): Running vgmstream on the extracted .snr files produces valid decoded .wav audio for both platforms, reporting Electronic Arts EA-XAS 4-bit ADPCM v1 (0x04) on PS3 and Xbox Media Audio 2 (0x03) on Xbox 360 with Electronic Arts SNR+SNS header metadata.
  • Pipeline Status: Basic extraction and decoding are complete across both platforms; the extraction and conversion path is wired into the game module pipeline via SetupMusicFiles.lua.
