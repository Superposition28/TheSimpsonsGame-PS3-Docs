Game format research · PS3 EU reference baseline

PARAM.SFO is a PSF key/value metadata file beside the PS3 game's USRDIR. It records title identity, display names, versions and platform flags. This page documents all three local PS3 copies and their binary layout; the demo package uses the same format at its own package root.

Binary layout and byte order

PSF is an indexed key/value container. The file consists of a 20-byte header, a 16-byte index record for each entry, a NUL-terminated key-string table, optional alignment padding, and the value-data area. All numeric header/index fields and integer payloads described here use little-endian storage. The four magic bytes are a literal signature, not evidence of a mixed-endian header.

File header; offsets are zero-based and range ends are exclusive
Offset Size / type Field Meaning
0x00 4 bytes Magic 00 50 53 46 — NUL followed by PSF.
0x04 uint32 LE Version Observed bytes 01 01 00 00 → 0x00000101.
0x08 uint32 LE KeyTableStart Absolute byte offset of the key-string area.
0x0C uint32 LE DataTableStart Absolute byte offset of the value-data area.
0x10 uint32 LE EntryCount Number of 16-byte index records starting at 0x14.

Version correction: the inspected reference exporter reads the version word as big-endian, yielding 0x01010000 from these bytes. The actual PSF field is little-endian 0x00000101. The exporter does not use that value or include it in its TOML output, so the matching exported key/value data does not validate its version interpretation.

The numeric layout is also documented by RPCS3's PSF header/index implementation. APP_VER and VERSION are separate string entries; neither is the binary header version.

Index records, relative offsets and allocation

16-byte index record at 0x14 + i × 0x10
Relative offset Type Field Interpretation
+0x00 uint16 LE KeyOffset Relative to KeyTableStart; points to a NUL-terminated key name.
+0x02 uint16 LE DataFormat Type tag; controls payload decoding.
+0x04 uint32 LE DataLength Used byte length. Includes the string terminator for observed 0x0204 entries.
+0x08 uint32 LE DataMaxLength Reserved byte capacity for this value, including any unused padding.
+0x0C uint32 LE DataOffset Relative to DataTableStart, not to this index record. 
index_pos = 0x14 + i * 0x10
key_pos   = KeyTableStart  + KeyOffset
value_pos = DataTableStart + DataOffset
used      = file[value_pos : value_pos + DataLength]
reserved  = file[value_pos : value_pos + DataMaxLength]

All observed value starts are aligned to four bytes, and unused allocation bytes are zero. The next value is located using its own index record; advancing by only the current used length skips the reserved capacity and is incorrect. Key names are ASCII in these samples. Text values use UTF-8, so byte length differs from character count when names contain ™, © or ®.

Value types and text encoding

PSF type tags; the char-array form is not present in these three samples
Type tag Stored bytes Payload Coverage
0x0204 04 02 NUL-terminated UTF-8 text; decode the used bytes and remove the terminator. Observed for names, IDs, version strings, category and license.
0x0404 04 04 Four-byte integer in little-endian order; preserving it as uint32 retains all bits. Observed for flags, bootable status and parental level.
0x0004 04 00 Length-delimited char array / opaque byte data, without an implied NUL terminator. Supported by common readers; not exercised by these files. Preserve bytes unless the specific key establishes text semantics.

The reference exporter tries UTF-8 decoding for 0x0004 and uses a printability heuristic before falling back to a RAW_HEX: string. That marker is an export convention, not an on-disk PSF signature or a fourth PSF type. Unknown type tags should remain explicit rather than being silently reclassified as text. The small non-negative integer values here do not establish the intended signedness of every possible PSF key.

EU has three additional localized-title slots compared with US. The demo adds ATTRIBUTE and TITLE_01, changes the title/category/ID, and declares 01.9000 instead of 01.9300. EU and demo use the same resolution mask, while US differs. All three share the same sound-format mask and license bytes. These differences describe the inspected files, not every PS3 release.

Flag names follow RPCS3's resolution_flag and sound_format_flag definitions. These values describe declared platform output support, not measured rendering resolution, playback results or the codec/channel layout of each SNU, SBK, MUS or VP6 asset. A mask is not a count of modes or channels.

Worked EU TITLE_ID record

EU EntryCount = 14, KeyTableStart = 0xF4, and DataTableStart = 0x180. The zero-based index record 12 starts at 0x14 + 12 × 0x10 = 0xD4:

000000D4  79 00 04 02 0A 00 00 00 10 00 00 00 24 04 00 00
  • KeyOffset = 0x79, so the key string is at 0xF4 + 0x79 = 0x16D: TITLE_ID followed by NUL.
  • DataFormat = 0x0204, DataLength = 10, DataMaxLength = 16.
  • DataOffset = 0x424, so the value begins at 0x180 + 0x424 = 0x5A4.
  • The ten used bytes encode BLES00142 plus NUL; six remaining allocated bytes are zero padding.

By contrast, EU RESOLUTION contains bytes 26 00 00 00 at 0x39C: little-endian integer 38, rather than four text characters or a big-endian value.

Parsing and validation checklist

  1. Require at least 20 bytes; verify literal magic 00 50 53 46 and decode the version as little-endian. Unsupported versions should be reported, not silently accepted.
  2. Check that 0x14 + 16 × EntryCount fits in the file. Check key/data table offsets and their order against the index end and actual file size.
  3. For each record, bound the key pointer within the key area and require a terminating NUL before the data area. Preserve case and reject or explicitly report duplicate keys.
  4. Check DataLength <= DataMaxLength and that both used and allocated ranges fit in the file. Validate any overlap before treating allocations as independent.
  5. Dispatch by the format tag. Require four used bytes for an integer; treat string lengths as byte counts and validate UTF-8 and termination. Keep unknown types as opaque bytes.
  6. Distinguish absent keys, empty strings and zero-valued integers. Preserve the raw version, type, capacity, offsets and padding when byte-for-byte reconstruction matters.

All 38 index entries across these three files passed the structural range, text and allocation checks. No whole-file checksum field was identified in the PSF header/index inspected here. SHA-256 values below are external identity measurements, not embedded integrity records.

What the TOML references preserve

The three linked TOMLs provide portable decoded key/value views and remain inside this documentation repository. Their string values preserve the observed UTF-8 text; integer entries become TOML integers. The referenced exporter was inspected to understand decoding behavior; it is not moved into the documentation repository, linked as a dependency, or required to read this page.

The TOMLs omit the PSF header version, type tags, relative offsets, used lengths, capacities and padding. They are therefore not lossless binary replacements, and no reverse conversion or byte-identical rebuild is established. Exporter choices such as UTF-8 replacement decoding, printable-array heuristics and a RAW_HEX string can also lose type information. Matching these three valid samples does not prove that every malformed or unknown-type file is handled correctly.

Related files and formats

  • EBOOT.BIN is the executable in the same PS3 source tree. PARAM.SFO identifies the surrounding game/package; it does not decode executable functions or establish an internal reference graph.
  • localetable.txt has a separate locale/configuration role. EU/US table identifiers match SFO TITLE_ID, but the demo locale table stores BLUS30065 while demo PARAM.SFO identifies NPEB90029. Preserve both observations rather than trusting the locale token as package identity.
  • The observed TITLE_XX entries are platform-facing display titles, distinct from LH2 localization strings, TOX subtitle timings and INF/TXD font assets. Matching language names do not establish shared IDs or pointers.
